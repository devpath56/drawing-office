# 1. The three departments are deep modules, and the lines between them are the whole interface

Date: 2026-09-07

## Status

Superseded by 3. The factory is one system of eleven containers inside one governance boundary
(2026-09-15): the three departments became one system whose machines are containers.

## Context

Three repositories do three jobs: design-loop's main pipe turns an utterance into a frozen requirement
(production), advisor-builder turns a role and a corpus into a deployed advisor (HR), and
learn-verify-kit turns a gap into a declared competence (L&D). Read on 2026-09-07, nine seams between
them exist in code — a path guessed twice, a check that shells a sibling's script, a stage that writes
into a sibling's spec directory — and none of the three models draws any of them. Four state
vocabularies are in use across the trees and agree on exactly one word, UNEVALUABLE.

## Decision

Each department is modelled as one software system whose interior a sibling never reads. Every seam is
a relationship between two containers, named for the code that carries it, and a seam the concept note
proposes but nothing on disk performs is drawn with a description that begins ABSENT, so the drawing
cannot claim it. The loop the factory depends on — an uncertain ruling becomes a gap, a declared weight
ranks a hire, the hire is what production recruits — is a dynamic view, and three of its hops are
ABSENT today.

## Consequences

A reader can see which seams are real and which are proposed without opening a file. The next edit to
any of the three trees that adds a sibling path without a corresponding relationship here is a drift
the model will not show, which is why the concept note's order of work puts a seams file per repo
before any new door. The picture is a claim about topology and says nothing about whether the
departments are any good; the checks in each tree answer that.
